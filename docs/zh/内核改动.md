# 内核改动说明

三个补丁都只改几行，但每个都对应一条“不加就完全用不了”的硬约束。下面按依赖顺序说明。

---

## 0001 sched：把 SYSVIPC 的成员挪进 Android ABI padding

**问题.** Flatpak 的沙箱要求内核有 `CONFIG_IPC_NS`。而在 `init/Kconfig` 里：

```
config IPC_NS
	bool "IPC namespace"
	depends on (SYSVIPC || POSIX_MQUEUE)
	default y
```

也就是说 `IPC_NS` 必须由 `CONFIG_SYSVIPC` 或 `CONFIG_POSIX_MQUEUE` 带出来。二者都是“会往结构体里塞字段”的选项：

- `CONFIG_SYSVIPC` 给 `struct task_struct` 加 `struct sysv_sem sysvsem; struct sysv_shm sysvshm;`（在 `#ifdef CONFIG_SYSVIPC` 里，位置在 `nameidata` 之后）；
- 一旦这两个成员出现，`task_struct` 后面所有成员整体位移，**任何类型里含 `task_struct` 的导出符号**的 genksyms CRC 都会变。

GKI 的厂商模块是靠 CRC 逐个校验加载的，于是：

```
msm_drm: disagrees about version of symbol module_layout
... 952 个模块无一能载入
```

实测：直接打开 `CONFIG_SYSVIPC=y` 后跑移植仓自带的 `tools/check-kmi.py`，对上游 release 里那 400+ 个厂商 `.ko` 得到 **11323 处 CRC 问题、1956 个不同符号**，重灾区是 `module_layout`（影响 404 个模块）、`devm_kmalloc`（224）、`__platform_driver_register`（217）。

**解法.** Android 在 `struct task_struct` 尾部留了 `ANDROID_KABI_RESERVE(1..8)` 专供厂商扩展。把这些预留槽拿来做 SYSVIPC 的成员，结构体布局在“开/关 SYSVIPC”两种情况下逐字节一致：

```c
 #ifdef CONFIG_SYSVIPC
-	struct sysv_sem			sysvsem;
-	struct sysv_shm			sysvshm;
+	// struct sysv_sem			sysvsem;
+	// struct sysv_shm			sysvshm;
 #endif
 ...
 	ANDROID_KABI_RESERVE(5);
+
+#ifdef CONFIG_SYSVIPC
+	ANDROID_KABI_USE(6, struct sysv_sem sysvsem);
+	_ANDROID_KABI_REPLACE(ANDROID_KABI_RESERVE(7); ANDROID_KABI_RESERVE(8), struct sysv_shm sysvshm);
+#else
 	ANDROID_KABI_RESERVE(6);
 	ANDROID_KABI_RESERVE(7);
 	ANDROID_KABI_RESERVE(8);
+#endif
```

这个做法不是我们发明的：[Droidspaces-OSS](https://github.com/ravindu644/Droidspaces-OSS) 的 `Documentation/resources/kernel-patches/GKI/below-kernel-6.12/` 里就有同名补丁（作者 `nullptr-t-oss`），用于在容器内核里安全打开 SYSVIPC。本项目的 `0001` 是它的等价实现。

**验证.** 用同一套 CI 分别编“开 SYSVIPC 但不打补丁”和“开 SYSVIPC 且打补丁”两个内核，比对 `Module.symvers` 与基线（原 fragment）的差异：

| 变体 | 关键 config | 补丁 | 共享符号 | CRC 漂移 |
|---|---|---|---|---|
| baseline | 原 fragment | 否 | 17090 | — |
| sysvipc | `SYSVIPC=y` + `IPC_NS=y` | **是** | 17090 | **0** |
| sysvipc-nopad | 同 sysvipc | 否 | 17090 | **10844** |
| mqueue | `POSIX_MQUEUE=y` + `IPC_NS=y` | 否 | 17090 | **0** |

对照实验说明两点：补丁确实把漂移清零（否则 10844）；而且**只开 `CONFIG_POSIX_MQUEUE=y` 也能带出 `IPC_NS`，同样零漂移、且完全不用改内核源码** —— 如果你不想碰 `task_struct`，这是更“干净”的一条路。

## 0002 module：放宽符号 CRC 比对

**问题.** 打完 `0001`，配置也逐项对齐（用 `extract-ikconfig.py` 从厂商内核里抠出内嵌配置，与本地构建的 `.config` 对比，仅 5 项不同、全是工具链版本串），编译器版本也对齐（`clang version 18.1.8`，与厂商内核的 `CONFIG_CC_VERSION_TEXT` 逐字一致），但本地构建出的 `module_layout` CRC 仍然是 `0x6500052f`，而厂商模块和上游 release 内核里的一切都指向 `0x4e276f37`。

现场统计（`modprobe --dump-modversions` 逐模块比对）：

```
refs_checked = 49680
distinct_crc_mismatch = 4306
missing = 2128
```

也就是说这不是某一个符号偶发不对，而是**整体 CRC 命名空间不同**。造成这种差异的可能因素还有构建环境（`CC_VERSION` 之外的 `LD`/`AR` 版本、`KBUILD_BUILD_*`、`genksyms` 版本、路径长度、`CONFIG_LOCALVERSION` 等），本项目没有继续追下去。

**解法.** 让 `check_version()` 直接通过：

```c
-		if (versions[i].crc == crcval)
+		if (1 || versions[i].crc == crcval) /* local: bypass GKI CRC mismatch */
 			return 1;
```

**这是本地权宜之计，不是上游质量的改动**：它关掉了“内核与模块 ABI 是否匹配”的守卫。换底包（厂商模块重建）之后仍能加载旧模块，出问题时不会再有 CRC 报错提示。使用者需要明白这一点。正确的长期解法是让重编内核复现厂商的 CRC —— 那需要精确复现构建环境。

**验证.** 打上后 `lsmod` 559 个模块全部进入，`dmesg | grep -c "disagrees about version"` = 0，桌面/GPU/WiFi/蓝牙全部正常。

## 0003 namespace：文件型挂载点不算“会泄漏”

**问题.** 前两个补丁到位后 `flatpak run` 仍然失败：

```
bwrap: Can't mount proc on /proc: Operation not permitted
error: ldconfig failed, exit status 256
```

排查结论（详见 [调试过程](调试过程.md)）：不是权限、不是 SELinux、不是缺 config，而是 `fs/namespace.c` 的 `mount_too_revealing()` 判定这个 procfs “会泄漏内容”。

判定链路：

```c
static bool mount_too_revealing(const struct super_block *sb, int *new_mnt_flags)
{
	if (ns->user_ns == &init_user_ns) return false;          // 我们是 userns，跳过
	if (!(s_iflags & SB_I_USERNS_VISIBLE)) return false;      // procfs 有 SB_I_USERNS_VISIBLE
	...
	return !mnt_already_visible(ns, sb, new_mnt_flags);       // 关键在这里
}
```

`mnt_already_visible()` 会遍历“同一 `s_type`、已经挂在父命名空间里”的挂载，对每个 `MNT_LOCKED` 的子挂载做“这个目录是不是永久为空”的检查：

```c
			if (!(child->mnt.mnt_flags & MNT_LOCKED)) continue;
			/* Is the directory permanetly empty? */
			if (!is_empty_dir_inode(inode)) goto next;   // inode 不是目录 => 恒不成立
```

而移植包为了让 llvmpipe 不生成 SVE 指令（SM8735 的 A720/A520 核不支持 SVE），把 `/proc/cpuinfo` 做成了**文件**：

```sh
sed -e 's/^\(CPU part\s*:\s*\).*/\10xd0b/' ... /proc/cpuinfo > /run/yupei-cpuinfo
mount --bind /run/yupei-cpuinfo /proc/cpuinfo
```

挂载点是普通文件 ⇒ `is_empty_dir_inode(inode)` 恒为 false ⇒ `goto next` 之后整棵树被判“会泄漏” ⇒ `-EPERM`。

因果实验（设备上直接验）：

| `/proc/cpuinfo` 状态 | userns 内 `mount -t proc` |
|---|---|
| 已 bind mount（默认开机状态） | **失败**（EPERM） |
| `umount /proc/cpuinfo` | 成功 |
| 重新 bind mount | 又失败 |

**解法.** 挂载点不是目录时，它不可能“藏起目录内容”，跳过这项检查：

```c
-			if (!is_empty_dir_inode(inode))
+			if (d_is_dir(child->mnt_mountpoint) && !is_empty_dir_inode(inode))
 				goto next;
```

**验证.** 同时满足：`/proc/cpuinfo` 仍是被伪装的文件（`mountpoint -q /proc/cpuinfo` 为真）、`bwrap --unshare-all --proc /proc` 通过、`flatpak run org.gnome.Calculator` 起来。

## 一起看

| 需求 | 需要的 config | 补丁 |
|---|---|---|
| Flatpak 沙箱 | `IPC_NS`（由 `SYSVIPC` 或 `POSIX_MQUEUE` 带出）、`USER_NS`、`PID_NS` | `0001`（若走 SYSVIPC）、`0002` |
| 沙箱里能挂 `/proc` | — | `0003` |
| 厂商模块能载入 | — | `0001`、`0002` |

`CONFIG_USER_NS` 本身**不需要** padding 补丁：`init/Kconfig` 里它没有 `depends on`，`struct cred` 里的 `user_ns`/`ucounts` 是无条件成员，`task_struct` 也不含 `CONFIG_USER_NS` 条件编译。

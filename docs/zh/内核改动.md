# 三个补丁分别在修什么

## `0001` sched：打开 SYSVIPC 不能再改变结构体布局

Flatpak 的沙箱要靠 `CONFIG_IPC_NS`，而在内核 `Kconfig` 里 `IPC_NS` 必须由 `CONFIG_SYSVIPC` 或 `CONFIG_POSIX_MQUEUE` 带出来。`CONFIG_SYSVIPC` 会往 `struct task_struct` 里插两个成员，插进去以后后面所有成员整体位移，凡是类型里带 `task_struct` 的导出符号，其 CRC 都会变——厂商模块就全部加载失败。

Android 在 `struct task_struct` 尾部专门留了预留槽给厂商扩展，把这两个成员放进预留槽，结构体在有/无 SYSVIPC 时布局一致：

```c
 #ifdef CONFIG_SYSVIPC
-	struct sysv_sem			sysvsem;
-	struct sysv_shm			sysvshm;
+	// struct sysv_sem			sysvsem;
+	// struct sysv_shm			sysvshm;
 #endif
 ...
+#ifdef CONFIG_SYSVIPC
+	ANDROID_KABI_USE(6, struct sysv_sem sysvsem);
+	_ANDROID_KABI_REPLACE(ANDROID_KABI_RESERVE(7); ANDROID_KABI_RESERVE(8), struct sysv_shm sysvshm);
+#else
 	ANDROID_KABI_RESERVE(6);
 	ANDROID_KABI_RESERVE(7);
 	ANDROID_KABI_RESERVE(8);
+#endif
```

做法来自 [Droidspaces-OSS](https://github.com/ravindu644/Droidspaces-OSS) 的内核补丁目录，它们用同样的办法在容器内核里开 SYSVIPC。

> 另一条不改源码的路：只开 `CONFIG_POSIX_MQUEUE=y` 也能带出 `IPC_NS`。如果你更在意"不动内核结构体"，可以只加这一项。

## `0002` module：本地重编的内核与厂商模块 CRC 对不上

打完 `0001`、配置也逐项对齐之后，本地编出来的内核仍会因为符号 CRC 与厂商模块不一致而拒绝加载任何模块，表现为开机定在 Logo、连 USB 都不出。

追到根因的代价很高（构建环境里除编译器版本外还有若干变量会影响 CRC 生成），这里先用放宽校验的办法让内核可用：

```c
-		if (versions[i].crc == crcval)
+		if (1 || versions[i].crc == crcval) /* local: bypass GKI CRC mismatch */
 			return 1;
```

**这是权宜之计**：它关掉了"内核与模块 ABI 是否匹配"的守卫。换底包之后旧模块仍会被加载，出问题时不会有 CRC 报错提示。真正的修法是让重编内核复现厂商的 CRC。

## `0003` namespace：文件型挂载点不该被判成"会泄漏"

前两个补丁到位后，`flatpak run` 还是失败：

```
bwrap: Can't mount proc on /proc: Operation not permitted
```

原因：移植包为了不让 llvmpipe 生成 SVE 指令（这颗 SoC 的核没有 SVE），把 `/proc/cpuinfo` 换成了一个**文件**的 bind mount。而内核在 user namespace 里挂 procfs 前会做一次安全检查：遍历已挂载的同类文件系统，对每个被锁定的子挂载问"这个目录是不是永久为空"。挂载点是普通文件时这个判断永远不成立，于是整棵 procfs 被判成"会泄漏内容"，直接 EPERM。

挂载点不是目录，本来也不可能藏住目录内容，于是跳过这项判断：

```c
-			if (!is_empty_dir_inode(inode))
+			if (d_is_dir(child->mnt_mountpoint) && !is_empty_dir_inode(inode))
 				goto next;
```

这样 `/proc/cpuinfo` 的伪装和 Flatpak 沙箱可以同时成立。

## 合起来看

| 需要什么 | 依赖 |
|---|---|
| Flatpak 沙箱能起来 | `IPC_NS`（由 SYSVIPC 或 POSIX_MQUEUE 带出）、`USER_NS`、`PID_NS`，以及 `0002` |
| 沙箱里能挂 `/proc` | `0003` |
| 厂商模块能载入 | `0001`、`0002` |

`CONFIG_USER_NS` 自己不需要额外补丁：它在 `Kconfig` 里没有依赖，也不改变 `task_struct` 的布局。

更细的排查路径（包括走过的死路）见 [调试过程](调试过程.md)。

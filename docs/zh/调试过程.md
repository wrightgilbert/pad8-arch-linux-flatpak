# 调试过程

记录一下从"Flatpak 起不来"到三个补丁的路径，重点是走过的死路，省得后来的人重走。

## 起点：一个反直觉的现象

同一台平板，Android 容器（Droidspaces + Debian）里 Flatpak 装上就能用，原生 Arch 里 `flatpak install` 一切正常、`flatpak run` 直接挂。差别在内核，不在 Flatpak。

读 Flatpak 源码可以确认：它给 bubblewrap 的参数是写死的 `--unshare-ipc`，这需要内核有 `CONFIG_IPC_NS`；而在内核 `Kconfig` 里，`IPC_NS` 只能由 `SYSVIPC` 或 `POSIX_MQUEUE` 带出来。容器内核之所以行，是因为 Droidspaces 的补丁在打开 SYSVIPC 的同时把结构体成员挪进了 ABI 预留位。

## 第一次尝试：直接打开 SYSVIPC

结果是不启动——屏幕定在开机 Logo。用移植仓自带的 `tools/check-kmi.py` 把厂商 `.ko` 与新内核的 `Module.symvers` 一比，问题很清楚：`task_struct` 成员一挪位，一大批导出符号的 CRC 全变，模块一个都加载不进来。

换成 ABI 预留位的写法后就对了。顺带发现另一条路：只开 `POSIX_MQUEUE` 也能带出 `IPC_NS`，同样不影响布局。

## 取证阶段：想靠日志定位，走不通

按老思路先找日志，全部失败：

- `/sys/fs/pstore` 一直是空的（ramoops 有保留区，但 kmsg_dump 不落盘）；
- `oops` 分区里只有上一个系统留下的旧快照；
- 内核配了 panic 不自动重启、控制台是 `ttynull`，崩了也不留东西。

结论：这种环境下"先拿日志再看"的思路不成立，得换个方向——**不比日志，比 ABI**。把设备上所有模块的 `modversions` 导出来，和本机内核的 `Module.symvers` 逐个对，立刻看出是整片不一致，而不是个别符号。

## 第二层问题：沙箱里挂不上 /proc

模块问题解决、系统能起之后，Flatpak 装得好、跑不了：

```
bwrap: Can't mount proc on /proc: Operation not permitted
```

排除法：不是权限（真 root 能挂）、不是 SELinux（没启用）、不是缺 config（四个 `CONFIG_*` 都在）、tmpfs 能在 user namespace 里挂、只有 procfs 不行。

在 `mount_too_revealing()` 上打点确认是它返回失败，再读代码发现它在遍历已挂载的同类文件系统时，会检查每个子挂载的挂载点"目录是不是空的"。而移植包为了不让 llvmpipe 生成 SVE 指令，把 `/proc/cpuinfo` 做成了**文件**的 bind mount——挂载点不是目录，这个判断永远不成立，于是整棵 procfs 被判成"会泄漏"。

三次对照实验（挂着 → 挂失败；卸掉 → 挂成功；再挂上 → 又失败）确认无误，补丁让非目录挂载点跳过这项判断。

## 事后看

- **代价最大的一步**是想用日志定位卡 Logo，那套设施在 GKI + `ttynull` 下基本无效。
- **最快见效的一步**是比 `Module.symvers` 与设备上 `.ko` 的 `__versions`，比任何日志手段都直接。
- 留了个尾巴：本地重编内核为什么复现不出厂商的 CRC，没有追到底，暂时用放宽校验绕过（见 `0002` 的说明）。

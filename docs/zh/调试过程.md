# 调试过程

记录一下这次从“Flatpak 跑不起来”到“三个内核补丁”的完整路径，包括走过的死路。所有数字都是在真机上跑出来的。

## 0. 起点：一个反直觉的现象

同一台平板：

- 在 **Android 容器**（Droidspaces + Debian 13 KDE）里，Flatpak 装上就能用；
- 原生 Arch Linux 里，`flatpak install` 一路正常，`flatpak run` 就挂。

差别不在 Flatpak，而在内核。

## 1. 读 Flatpak 源码，确认硬需求

`common/flatpak-run.c` 里给 bubblewrap 的参数是写死的：

```c
flatpak_bwrap_add_args (bwrap, "--unshare-ipc", NULL);
flatpak_bwrap_add_args (bwrap, "--unshare-net", NULL);
...
```

`--unshare-ipc` 需要内核有 `CONFIG_IPC_NS`。而 `init/Kconfig` 里：

```
config IPC_NS
	bool "IPC namespace"
	depends on (SYSVIPC || POSIX_MQUEUE)
	default y
```

容器内核之所以行，是因为 Droidspaces 给的内核补丁把 `CONFIG_SYSVIPC` 打开了 —— 但它是**打了 Android ABI padding 补丁**之后再打开的。原生移植的内核没有这一步。

## 2. 第一次尝试：直接打开 SYSVIPC（失败）

设备上跑移植仓自带的 `tools/check-kmi.py`，把 400+ 个厂商 `.ko` 与新内核的 `Module.symvers` 比对：

```
11323 problem(s), 1956 distinct bad symbols
  module_layout                  404 modules
  devm_kmalloc                   224
  __platform_driver_register     217
```

刷进设备后屏幕定在开机 Logo，连 initramfs 的 USB gadget 都不出。

补丁前后对照（CI 编的同一套配置，只有补丁不同）：

| 变体 | 共享符号 | CRC 漂移 |
|---|---|---|
| baseline（原 fragment） | 17090 | — |
| SYSVIPC + padding 补丁 | 17090 | **0** |
| SYSVIPC 无 padding（对照） | 17090 | **10844** |
| 只开 POSIX_MQUEUE | 17090 | **0** |

结论：padding 补丁在 6.6 上有效；`POSIX_MQUEUE` 也能单独带出 `IPC_NS` 且零漂移。

## 3. 装机：底包选错会带来另一个量级的问题

平板当时是澎湃 OS **4.0.10**，而上游要求 **4.0.5**。把 4.0.10 的 `/vendor_dlkm` 模块拉下来看 vermagic：

```
6.6.57-android15-8-g34b7c5063ce7-4k   (289 个)
6.6.57-android15-8-4k                 (99 个)
6.6.57-4k-g34b7c5063ce7               (16 个)
```

它们是 OEM 自己的 **6.6.57** 供应商树编的，与 GKI `6.6.118` 不是一个东西，CRC 必然不一致。最终按上游要求回到 4.0.5 底包。

## 4. 刷入自编内核 → 卡 Logo，且拿不到日志

打了 padding 补丁、配置也一致的三个内核（CI 编的、平板原生编的）全部卡在开机 Logo。取证全灭：

- `/sys/fs/pstore/` 一直是空的（ramoops 有保留区、有注册日志，但 kmsg_dump 不落盘）；
- `/dev/sda24`（`oops` 分区）里只有 HyperOS 时代的旧快照；
- 内核 `CONFIG_PANIC_ON_OOPS=y` + `CONFIG_PANIC_TIMEOUT=-1` + cmdline `console=ttynull` ⇒ panic 也不会自动重启，不会留下任何东西。

于是换了个思路：**不去猜内核为什么崩，而是直接比“内核认为的 ABI”和“模块要求的 ABI”**。

## 5. 破局：比对 952 个模块的 modversions

```bash
for m in /lib/modules/$(uname -r)/**/*.ko*; do modprobe --dump-modversions "$m"; done
```

结果非常干净：

- 所有模块（含厂商 6.6.57 的）的 `module_layout` = **`0x4e276f37`**；
- 我们编的内核 `Module.symvers` 里 = **`0x6500052f`**。

逐符号统计：`refs_checked=49680`、`distinct_crc_mismatch=4306`、`missing=2128`。这不是偶发差异，是整个 CRC 命名空间不同。既然源码 tag、`.config`（用 `extract-ikconfig` 从厂商内核里抠出来逐项比过，只有 5 项工具链串不同）、编译器版本（`clang version 18.1.8`）都对得上，就先用绕过校验的办法验证假设：

```c
-		if (versions[i].crc == crcval)
+		if (1 || versions[i].crc == crcval)
```

刷入后：`lsmod` 559 个模块全部载入，`dmesg | grep -c "disagrees about version"` = 0，桌面正常。**假设成立**：卡 Logo 就是模块全部被拒载导致的。

## 6. Flatpak 起来了，但沙箱里挂不上 /proc

装上 Flathub 的 `org.gnome.Calculator`（GNOME Platform 51 + Mesa 26.2.5，2.5 GB）后：

```
bwrap: Can't mount proc on /proc: Operation not permitted
error: ldconfig failed, exit status 256
```

排查顺序与结论：

| 检查 | 结果 |
|---|---|
| `bwrap` 带 setuid 位 | 是 ⇒ `chmod 755`（我们提供了 `USER_NS`，setuid 模式会被 bwrap 拒绝） |
| 缺 config？ | 否：`SYSVIPC/IPC_NS/PID_NS/USER_NS` 全开 |
| SELinux？ | 未初始化（`/sys/fs/selinux` 不存在），LSM = `capability,selinux,bpf` |
| 真 root 能挂 proc？ | 能（`sudo unshare -p -f --mount-proc true`、`sudo mount -t proc` 都 OK） |
| userns 里能挂 tmpfs？ | 能（rc=0） |
| userns 里能挂 proc？ | **不能**（EPERM） |

kprobe 逐层打点（`tracefs/kprobe_events`）：

```
mount_capable         -> 0x1                 权限没问题
sget_fc               -> 0xffffff8885d42000  super_block 拿到了
proc_fill_super       -> 0x0                 填充成功
security_sb_kern_mount-> 0x0
mount_too_revealing   -> 0x1                 ← 就是它
```

`do_new_mount_fc()` 里：

```c
if (!error && mount_too_revealing(sb, &mnt_flags))
	error = -EPERM;
```

再读 `mnt_already_visible()`：它对同类型已挂载树里的每个 `MNT_LOCKED` 子挂载问“这个目录是不是永久为空”。而移植包为了**让 llvmpipe 不生成 SVE 指令**（SM8735 的 A720/A520 没有 SVE），把 `/proc/cpuinfo` 做成了文件型 bind mount：

```sh
mount --bind /run/yupei-cpuinfo /proc/cpuinfo
```

挂载点是文件 ⇒ `is_empty_dir_inode()` 恒 false ⇒ 整棵 procfs 被判“会泄漏”。

直接做因果实验，三次可复现：

| `/proc/cpuinfo` | userns 内 `mount -t proc` |
|---|---|
| bind mount（开机默认） | FAIL |
| `umount /proc/cpuinfo` | OK |
| 再次 bind mount | FAIL |

## 7. 修复与最终验证

```c
-			if (!is_empty_dir_inode(inode))
+			if (d_is_dir(child->mnt_mountpoint) && !is_empty_dir_inode(inode))
 				goto next;
```

刷入后一次通过：

```
内核：6.6.118-4k-arch+
/proc/cpuinfo      挂载中（llvmpipe 仍被保护）
bwrap --unshare-all --proc /proc   通过
flatpak run org.gnome.Calculator   起来，沙箱内 /app 可读
lsmod                              559
dmesg "disagrees about version"    0
```

## 8. 复盘：时间都花在哪

| 阶段 | 代价 | 说明 |
|---|---|---|
| 误以为配置不一致 | 半天 | `extract-ikconfig.py` 从内核镜像里抠出内嵌配置才排掉 |
| 想靠日志定位卡 Logo | 一天 | pstore / oops 分区 / mtdoops 全部无效，这条路在 GKI + `console=ttynull` 下基本走不通 |
| 比对 modversions | 两小时 | 真正的破局点，早该先做这个 |
| `/proc` EPERM | 半天 | kprobe + `umount` 对照实验，定位很快 |

**教训**：设备起不来又没日志时，先比 `Module.symvers` 与设备上 `.ko` 的 `__versions`，比任何日志手段都快。
